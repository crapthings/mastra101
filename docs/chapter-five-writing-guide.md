# 第五章写作指南：提示词

## 章目标

教读者写清系统与用户提示词，并由维护者根据可观察的结果保留、修改或删除规则。目标是掌握可迁移的方法，为后续使用模型框架做准备。

本章为通用知识，不依赖 04 的代码、供应商或下载项目。实验入口仅简短提及 Mastra Studio 是一种选择，不介绍安装、密钥、注册 Agent 或配置文件。

## 节目标与段落推进

| 节 | 节目标 | 推进 |
| --- | --- | --- |
| 对照实验 | 建立独立比较方法 | 通知改写 → 控制条件 → 记录结果 → 指令分工 |
| 系统提示词 | 维护通用规则与边界 | 长期与当前 → 指令入口 → 可检查规则 → 优先级 → 默认值 → 验证 |
| 用户提示词 | 表达具体任务 | 目标、材料、范围、完成标准 → 具体约束 → 对照 |
| 角色设定 | 分清工作视角与模拟 | 关注点 → 职责 → 虚构接待练习 → 证据边界 |
| 表达方式 | 改变表达而不改变事实 | 读者用途 → 具体表达要求 → 相同信息的两种表达 → 不确定性 |
| 材料与示例 | 保留来源和语义 | 完整材料 → 指令边界 → 示例不混入事实 → 组织结构 |
| 结构化输入 | 组织已有内容 | 自然语言 → Markdown → XML → JSON 数据 → 方法取舍 |
| 结构化输出 | 选择格式并设计可检查的数据结构 | 用途 → JSON/JSONL/YAML/XML/CSV → headers + rows → 列位置与缺失值 → 三层检查 |
| 语义标记与解析 | 设计可提取的自定义协议 | 提取目标 → 标记样例 → 解析约定 → 格式取舍 → 语义分片 → 完整边界 → 保存断点 → 重试与核对 |
| 验证提示词 | 维护有证据的规则 | 问题 → 候选规则 → 比较 → 正常与其他情况 → 记录 → 取舍 |

## 教学例子

用独立的会议通知、会议资料、活动接待模拟等日常任务说明方法。所需文字直接给在正文，不要求读者找到前章代码或某个项目文件。例子不构成真实会议或活动记录。

JSON 仅演示材料与结果的组织，不使用框架 API。界面不提供系统指令入口时，不能把在普通聊天框写“系统提示词”当成改变了角色。

## 核心立场

- 开发者从实际问题提炼规则，明确适用条件和可见检查标准。
- 模型可以起草、整理或发现矛盾；维护者负责业务含义、验证证据与取舍。
- 长模板、标签和角色称号不等于有效规则；篇幅本身不是质量标准。
- 每条长期规则应能说明存在原因、适用范围和验证方法。调试记录保留在提示词之外。
- 指令优先级不是百分比权重，也不是执行保证。不同接口应核对其角色约定；正文以 OpenAI 为已注明来源的例子，不声称所有服务实现相同。
- 默认值与必须遵守的边界分开，允许用户在授权范围内定制任务。

## 图示

## 正文表达约束

## 输出格式与紧凑结构

保留“结构化输出”为一节，内部先比较格式，再设计数据结构，不把 headers + rows 当作另一种文件格式。

使用同一组两场会议数据对照 JSON 对象列表、JSONL、YAML、XML 与 CSV：
- JSONL 每行独立有效，不写外层数组或行间逗号；未完成行不能作为有效记录。
- YAML 展示缩进、明确字符串与数字类型；XML 的 missing 属性是示例约定，不是内建 null。
- CSV 明确表头、字段转义和类型/空值由接收方约定。
- headers + rows 减少重复键名，但必须维持唯一表头、固定顺序、行长和类型；null 保留缺失位置。
- 不承诺固定 Token 节省比例。字段多变、记录少或嵌套复杂时，对象列表可能更易维护。
- 原输出检查图移至格式与结构设计之后，仍以 JSON 为具体例子。

新增 jsonl、yaml、xml、csv 的 Shiki 语法按需加载，不引入新依赖或全语言包。已核对高亮结果逐字保留原文，并使用 JSON、逐行 JSON、YAML、XML 与 CSV 解析验证例子表达同一数据；headers/rows 可按列名还原为原对象列表。

格式依据：

- https://jsonlines.org/
- https://yaml.org/spec/1.2.2/
- https://www.w3.org/TR/xml/
- https://www.rfc-editor.org/rfc/rfc4180


## 语义标记与程序解析

在结构化输出之后单设“语义标记与解析”一节，不将它包装为行业标准或模型特殊 Token。沿用相同两场会议数据，在自然语言中以 record/字段的成对标记圈定程序要提取的片段；location 中 ∅ 表示缺失。

约定固定字段顺序、每字段一次、无嵌套、记录完整闭合、类型转换和错误处理。正文中的普通数字不参与提取。保留标记冲突应报错，本节没有省略实现却暗示已经具备转义能力。流式片段必须区分未完成和非法结果。

用户反馈的 Gemini JSON 输出失败用作考虑替代格式的动机，不写成通用性能结论。区分提示词要求 JSON、原生结构化输出、截断与解析失败。依据 https://ai.google.dev/gemini-api/docs/structured-output 核对其原生能力和限制；自定义协议需在同样场景下比较，不能断言必然更稳或更省 Token。

本次仅提供协议与数据示例，未新增生产解析库，也未对任一模型实际生成效果作验收。

语义标记已从结构化输出拆为独立第九节 /prompts/markers，第十节为验证提示词。结构化输出保留标准格式与 headers/rows 设计；新节单独讨论协议、解析及错误处理，不新增生产解析库。05 仍保持两级目录。


## 分片与断点

语义标记节进一步讲大量内容的语义分片、外层 chunk 与记录 ID、程序检查覆盖范围、断点恢复及合并校验。以两条会议记录示意一个批次，不声称已经处理了真实大量材料。

分清三个边界：输入材料的语义切分位置、输出协议的完整分片边界、程序持久保存后的恢复断点。网络流式片段不等同业务分片，也不保证完整标记在同一网络片段到达。

批处理标记是对前文单记录协议的明确扩展。编号与来源由程序指定，模型原样返回；闭合标记不能证明记录无遗漏。断点由应用维护，不依赖模型记忆。源版本、切分方案与规则版本变化需要重新确定可复用结果。

结果保存后推进断点；为中间崩溃后的重放保留稳定标识和幂等处理。并行场景记录每片状态，避免把最大成功编号误认为连续完成。最后核对完整性、重复与跨片关系，不宣称分片消除了上下文限制。

此处为设计知识，未新增生产分片解析器、持久化系统或自动执行流程。
