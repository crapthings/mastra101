# 正文与本节检查的统一准则

## 面向读者的推进

每章解决一个阶段的问题，每节回答其中一个具体问题。段落先给当前情境，再说明概念与判断方法，最后由尚未解决的问题引出后文。章目标、节目标和段落目标留在写作指南，不直接写成正文提示语。

使用自然中文与真实任务形态；教学例子必须明确哪些材料为作者编写，哪些结果经过实际运行。技术名词在首次解释或承担关键含义时加粗，不把整段话都强调。绿色用于可迁移的结论，红色用于容易误判的边界，避免重复正文和相邻提示框。

## 本节检查

统一使用“本节检查”标题。题目应能根据本节与前文回答，使用已有场景，要求读者作出区分、修改或核对，而不是只寻找关键词。通常一至两个相互承接的问题即可，不为保持形式一致给所有题目硬加 Agent。

| 章 | 检查目标 | 不提前要求的内容 |
| --- | --- | --- |
| 01 大语言模型 | 分清参数、输入、依据、工具结果与调用循环 | 不要求搭建项目或掌握 Agent 框架 |
| 02 框架体系 | 判断状态、记忆、流程与运行支撑各解决什么问题 | 不背接口名称，不把框架当成唯一方案 |
| 03 快速开始 | 从实际调用记录判断路径是否接通、工具是否执行、结果是否可靠 | 不把配置复述、脚本退出或答案流畅当成验收 |
| 04 核心组件 | 区分配置、数据流、作用范围与执行控制 | 不提前扩成完整生产项目 |
| 05 提示词 | 写清任务与规则，用可观察结果决定是否保留改动 | 不以长模板、标签数量或模型自评代替证据 |
| 06 模态 | 判断不同输出如何供 Agent 使用，保留来源、条件与失败状态 | 不把每项练习变成部署、模型选型或完整控制系统设计 |

检查题中的正确做法必须在正文找到依据。开放题不要求唯一措辞，但要能说明检查的是哪种错误。配置问题应关联实际请求路径；输出问题应关联后续用途。
