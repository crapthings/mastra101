# 第四章写作指南：核心组件

## 章目标

读者能解释 Mastra 各核心组件的职责，沿一次任务说明它们如何配合，并根据需求判断应该增加哪种能力。03 负责跑通，04 负责拆解；不把官方参考目录逐项搬进教程。

## 阅读顺序与节目标

| 节 | 节目标 | 引向下一节的缺口 |
| --- | --- | --- |
| 智能体 | 分清 Agent 配置、一次运行与一次模型调用 | 工具请求究竟怎样落到执行 |
| 工具 | 分清说明、结构检查、业务检查与执行责任 | 返回结果怎样被模型看到 |
| 上下文 | 判断本次调用实际获得哪些信息 | 跨次调用的信息由谁保存和取回 |
| 记忆 | 区分历史、长期信息、会话范围与存储 | 保存信息不能规定任务顺序 |
| 工作流 | 理解显式步骤、数据流和 Agent 的组合 | 等待确认时如何暂停与继续 |
| 运行与控制 | 区分停止、审批、恢复与 Harness | 可复用的做事方法怎样组织 |
| 技能 | 分清任务说明、执行能力与强制流程 | 方法被读取后，效果怎样检查 |
| 追踪与评估 | 区分过程证据和质量标准 | 为后续输入表达与模态学习建立组件边界 |

## 段落推进

以下是内部写作依据，不显示为正文中的“段落目标”。每个编号对应一个正文小节；箭头表示该小节前后自然段的推进。

### 智能体

1. 接住 03 一次任务中的多步记录 → 交代沿用现有项目的阅读方式。
2. 定义 Agent → 用职责表区分 Agent 配置、generate 输入和运行选项，说明修改需求应落在哪一处。
3. generate 发起任务 → 一次任务可以包含多次模型调用。
4. 指令参与模型调用，配置与校验由程序落实 → 根据请求前后定位问题。
5. 独立 Agent 与 Mastra 实例的分工 → 引出具体工具执行。

### 工具

1. clock 能直接调用 readTime → 模型参与选择时，需要工具接口及 Agent 挂载。
2. 模型与执行程序各需什么 → 将接口说明、输入输出和实际代码对上。
3. 参数结构正确 → 仍需检查有效时区与业务条件。
4. 只读查询扩展为修改操作 → 权限和重复执行由程序负责。
5. 结果需要足够明确 → 引向结果进入上下文。

### 上下文

1. 追问依赖前文 → 定义一次调用的信息范围。
2. 区分指令、需求、工具与结果 → 明确来源后再核对依据。
3. 同次运行的结果回传 → 区分跨次调用的历史保存。
4. 容量和相关性问题 → 选择信息并检查压缩损失。
5. 临时事实与持续偏好 → 引出保存与取回。

### 记忆

1. 偏好可复用、时间需更新 → 记忆提供背景，不训练权重。
2. resource 与 thread → 对象和会话的范围区别。
3. 先掌握消息历史与工作记忆 → 语义召回和观察记忆只识别用途，按长历史问题再引入。
4. Storage 与 Memory → 区分保存位置和调用使用，明确持久化。
5. 用追问检查记忆 → 记忆不能替代流程安排。

### 工作流

1. 明确业务顺序 → 定义工作流的执行职责。
2. 定义步骤 → 组合定义与实际运行分开。
3. 步骤连接 → 数据结构必须衔接。
4. 从资料齐全与缺失引出分支 → 明确每步的完成条件。
5. 流程等待确认 → 引出暂停、恢复与运行管理。

### 运行与控制

1. 步数与超时 → 终止不等于成功或回滚。
2. 需要人确认的动作 → 审批落在 execute 之前。
3. 暂停所需状态 → 快照与记忆的区别、各机制的恢复接口 → 拒绝动作后仍可能继续响应。
4. 跨请求持续工作 → Harness 是一组能力，不是超时别名。
5. 按需求选运行机制 → 引向可复用任务方法。

### 技能

1. 重复任务的方法 → 技能是说明与资料，不是权重。
2. 工具动作与任务方法 → 技能不会凭空增加工具能力。
3. createSkill 与 skills → SKILL.md 文件形式。
4. 发现和读取技能 → 读取不等于强制遵守。
5. 从一项重复任务开始 → 用执行证据检查效果。

### 追踪与评估

1. 从 03 的记录出发 → Trace 和 Span 组织过程。
2. 日志、追踪、指标 → 说明必须配置，避免暗示开箱已有完整记录。
3. 无异常仍可答错 → 用任务完成标准定义评估。
4. 程序检查与模型评分 → 标准和依据决定分数意义。
5. 用现实缺口定位组件 → 用追踪与完成标准验证新增能力，保留 05 的内容边界。

## 示例与实现

- 沿用时间查询和旅行安排。会议与提醒仅作职责解释，不声称已实现这些操作。
- 第一节用职责表对照 03 的真实代码，不再次展示完整 Agent 文件。04 当前无独立代码块，两种代码语言偏好下使用同一份概念正文；03 的代码切换保持原样。
- 第一版侧重概念与现有代码对照，不声称已提供 Memory、Workflow、Harness、Skills 的独立运行项目。
- 八节各有 lazy 路由；入口只加载目录元数据。03 最后一节连接 /core，04 内部上一节与下一节连续。
- 配置与运行、记忆读取、工作流组合、工具审批、技能分工各配一张 SVG 图；工具、上下文、评估保留正文与表格，不为每节强行配图。
- 绿色用于可迁移结论；红色用于容易导致错误实现的认知边界，不用于装饰一般术语。

## 边界

- 提示词组织、角色与表达留给 05；文字、图片、视频、音频的材料处理留给 06。
- 不展开高级路由、检索系统、多智能体、持久执行基础设施和完整评估工程。
- 不把 Memory 等同 Storage，不把快照等同会话历史，不把技能等同工具或强制流程。
- Harness 以本地文档的持续运行与外部控制职责为准，03 的 maxSteps 仅是进入运行控制的起点。
- SDK/API/网关的关系不再复讲；模型配置仍沿用 03 的 Vercel 路径。

## 图文位置与表达边界

| 节 | 放置位置 | 图要说明什么 |
| --- | --- | --- |
| 智能体 | 调用之后，循环才开始 | Agent 配置在运行之外，一次 generate 可以包含多次模型调用 |
| 记忆 | 从存储到本次上下文 | 已保存的信息经过取回与整理，和新消息、工具新结果共同提供上下文 |
| 工作流 | 连接的是数据，不只是箭头 | 固定流程中的某一步可以调用 Agent，箭头传递明确的数据 |
| 运行与控制 | 暂停之后，靠什么继续 | 批准才执行动作；拒绝返回拒绝信息，两路均可继续响应 |
| 技能 | 先找到技能，再读取内容 | 技能提供方法，Agent 请求已接入工具获得真实结果 |

图文统一沿用旅行与时间场景，未实现的提醒与预约查询明确标为概念示意。蓝色表示关注的位置，不表示成功状态。图示文案保存在 src/locales/diagrams，随相应节的独立路由加载。无新依赖、外部模型请求或交互控件。


## 03 → 04 的衔接

03 以三种查询场景验收项目，然后留下两个已经能观察到的问题：一次 generate 为什么有多步记录，readTime 为什么还需要工具包装。04 的前两节分别接住这两个问题，不重新安装项目或重复整份代码。

04 的深化点是职责和实现决策：怎样区分配置与本次输入、函数与工具接口、同次运行与跨次记忆。新能力继续按实际需求引出。记忆先掌握历史与工作记忆，其余形式作为后续问题的入口；工作流中的前置条件明确是示例业务规则。

当前结构与五张图保留；后续修改优先依据实际阅读或运行反馈，避免继续增加术语或同义提醒。
