# 第二章写作指南

内部编辑使用，不展示给读者。沿用第一章的中文排版、术语加粗和色块准则。

## 章目标

读者能从持续使用的旅行任务中辨认状态、记忆、流程、运行支撑和质量检查各自解决的问题，理解它们怎样配合，区分框架的通用机制与应用的业务判断，再进入 Mastra。

## 本轮评估与处理

| 原有问题 | 调整 | 验收依据 |
| --- | --- | --- |
| 状态与记忆容易被读成互斥的存储分类 | 按任务进展与信息使用区分，明确可重叠且都能成为上下文来源 | 任务节末尾、记忆节第二小节 |
| 工作流目标过度强调固定顺序 | 展示确认、修改、等待三个分支，说明步骤可包含调用循环 | 工作流第二小节及练习 |
| 驾驭偏向约束和安全提醒 | 先讲条件与反馈，再讲执行检查和运行支撑 | “支撑持续运行”四个小节 |
| 观察与评估像术语介绍，缺少判定依据 | 用偏好失效的同一个案例解释排查和质量标准 | 观察与评估正文及练习 |
| 框架和 Harness 关系不够明确 | 区分可复用结构与实际运行系统，避免默认接入即具备完整能力 | 框架的作用第三、四小节 |
| 个别练习要求未提供的信息或泛泛列举 | 改为判断已给出的情境，提出可核查的答案 | 前六节练习 |

## 内容边界

- 保持前六节顺序：先保存进展，再保留相关信息，再组织步骤、支撑运行、检查质量，最后说明框架作用。
- 章内使用具体案例解释机制，不展开产品 API、数据库设计、恢复算法或评估实现。
- 状态、记忆和上下文是关注角度不同的概念，不假设必须对应三套独立存储。
- 工作流不等于只能按固定直线执行，也不与模型调用循环互斥。
- Harness 指实际运行支撑，范围依实现而异；框架可用于构建它，但不与它完全等同。
- 第七节“Mastra”介绍框架与 Agent 的基本职责，再引向第三章实践。
- 保存状态不保证安全重试；保存记忆不保证正确选取；评估通过不保证所有任务可靠。
- 每节只加粗新定义或关键区分，不在后文重复强调同一术语；提示框只提炼有价值的结论或具体误解。
- 章末以共同接口和执行结构的需求引出 Mastra，不宣传框架能自动解决所有问题。

## 节目标与段落推进

每个编号对应正文的一个小节，箭头表示自然段间的推进。正文不展示内部目标标签。

### 1. 保存任务进度

节目标：理解应用如何记录任务进展，并在中断后判断能否继续。

1. 从跨日确认引出持续任务 → 列出继续处理所需信息。
2. 定义并展示一份进度记录 → 解释聊天记录不能单独替代明确状态。
3. 用响应丢失说明结果未知 → 要求恢复之前核对依据。
4. 按任务进展与偏好用途区分信息 → 承认信息可重叠并引出记忆。

### 2. 记忆如何生效

节目标：理解信息怎样从保存的记录进入当前请求，并区分长期偏好与本次条件。

1. 用下次旅行少问一次引出需求 → 定义应用记忆。
2. 展示保存、选择、注入的过程 → 解释状态与记忆都可提供上下文。
3. 区分本次条件与长期偏好 → 用临时例外解释适用范围和更新。
4. 让记忆与任务状态一起提供起点 → 引出确认之后的执行关系。

### 3. 组织任务步骤

节目标：理解工作流如何组织步骤、分支和等待，并与模型的调用循环配合。

1. 回顾按结果改变下一步 → 对照必须遵守的确认顺序。
2. 定义分支和等待 → 说明步骤内部仍能灵活调用模型。
3. 用跨日确认解释暂停 → 指出恢复需要关联的方案和状态。
4. 区分顺序正确与参数正确 → 引出运行检查。

### 4. 支撑持续运行

节目标：理解怎样通过信息、工具、反馈和执行检查，支撑模型持续完成任务。

1. 列出完成查询所需的条件 → 说明准备运行环境的作用。
2. 展示真实结果和失败反馈 → 连接执行、记录、继续或停止。
3. 用人数不符说明操作检查 → 说明确认内容变化后需要重新判断。
4. 为前述机制引入 Harness 名称 → 引出如何验证运行是否有效。

术语参考：[Anthropic：Effective harnesses for long-running agents](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)。借鉴其模型周围运行支撑的概念；旅行案例和章节组织由教程自身构建。

### 5. 观察与评估

节目标：分清“执行经过什么”和“结果是否合格”，为改进应用建立依据。

1. 用偏好失效列出不同错误来源 → 指出需要关联哪些执行信息。
2. 定义可观测性并定位缺失环节 → 约束日志记录范围。
3. 定义评估并给出可检查场景 → 解释前后比较及覆盖范围的限制。
4. 将检查依赖连回前文机制 → 引出一致组织方式。

### 6. 框架的作用

节目标：看清应用增长后需要维护的通用机制，判断什么时候值得引入框架。

1. 承认简单调用可以手写 → 用用户需求增长引出多项机制。
2. 用等待确认展示关联工作 → 用格式变更说明长期维护成本。
3. 说明这些工作跨业务重复 → 定义框架可复用机制的价值。
4. 说明学习与约定的成本 → 保留手写方案，明确框架、Harness 与业务分工。
5. 以 Mastra 作为贯穿实践的框架 → 说明最小例子用于认识接口，实际价值随需求增长检验。

动机写作边界：不声称所有应用必须使用框架，也不凭功能数量论证价值；用需求变化会牵动哪些代码，解释采用框架的理由。

## 图示安排

- 记忆第二小节：切换餐厅推荐与天气查询，观察信息选择；明确没被选取不等于删除，状态与记忆也不要求独立存储。
- 工作流第二小节：切换确认、修改和等待，显示分支、返回及恢复；不模拟真实提交。
- 支撑持续运行第四小节：用运行支撑范围包围输入、模型和执行，并展示真实反馈回路。
- 框架第三小节：区分业务决定、通用机制和外部服务；明确接入框架仍需配置与验证。
- 保存任务进度已有具体进度记录案例；观察与评估已有同一案例的两种检查方式，暂不为它们追加装饰性图示。
- 新图随对应章节加载；中文资源保存在独立命名空间。蓝色仅表示当前交互状态，绿色和红色仍保留给正文结论与误解提示。


## 与 01、03 的衔接

01 以同一任务中的调用循环收尾，02 从“循环结束，但用户明天才确认”继续，明确任务状态服务于尚未完成的整件事。旅行场景用于解释需求，不暗示上一章已实现旅行应用。

02 收尾先说明框架的采用取决于维护需求，再交代 03 为什么缩小为时间查询：数据来源明确、结果可核对，无需先接入预订服务和数据库。03 只验证模型请求、工具执行和结果回传，其他能力随后逐项展开，避免让读者以为短例子已经实现本章全部机制。
