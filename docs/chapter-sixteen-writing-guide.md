# 第十六章写作指南：追踪与指标

## 章目标

承接 15 的外部连接，让读者能关联一次活动查询的执行记录，区分执行状态与业务完成，用指标发现变化，再回到追踪和日志查证。结果质量评估留给后续章节。

## 节目标与段落推进

| 节 | 节目标 | 段落推进 |
| --- | --- | --- |
| 观测配置（Observability） | 接通采集、导出与存储 | 外部查询慢 → 三站职责 → 组合存储 → 下载与实验 → flush/关闭 → 执行树 |
| 执行树（Trace & Span） | 按层级与时间理解一次执行 | Trace/Span → 标识 → 耗时重叠 → Agent 工具实例 → 远端可见范围 |
| 追踪关联（Trace Context） | 从业务请求找到具体运行 | 查询单号 → requestId/runId/traceId/spanId → 提取字段 → 分类与精确定位 → 状态含义 |
| 执行结果（Execution Outcomes） | 区分执行成功与业务完成 | 资料缺失 → 三模式 → 字段与版本 → maxSteps → 按原因恢复 → 日志 |
| 日志关联（Logging） | 查询某次运行的现场细节 | 树缺少决策背景 → logger → 两个级别门槛 → span 关联 → 采集字段 |
| 采集范围（Data Capture） | 验证隐藏、脱敏与采样的边界 | 记录副本 → 隐藏不影响运行 → 日志边界 → 字段脱敏 → 采样口径 |
| 指标查询（Metrics） | 查询自动指标并解释统计范围 | 单次到整体 → 三个样本 → 范围/聚合/分页 → 分布 → Token/费用缺失 |
| 排查路径（Diagnosis） | 从整体变化定位具体证据 | 慢样本 → traceId → 步骤/日志 → 验证修复 → 内容质量未解决 |

目标仅用于编辑，不进入正文。本节检查围绕能否把输出交给后续 Agent，而非背诵字段。

## 实现与边界

- Node.js >=24；固定 core 1.80.0、observability 1.22.0、duckdb 1.16.0、libsql 1.27.1、zod 4.6.7。
- 十个源文件：两个辅助模块与八个入口，JS/TS 各一份。仅 02 请求模型；沿用 vercel/openai/gpt-6.1-sol、AI_GATEWAY_API_KEY。
- 真实 Mastra 工作流采集、MastraStorageExporter 写入、DuckDB 原生查询。LibSQL 不冒充支持指标；本实验都为内存数据库，退出清空，不宣传持久化。
- flush 后查询；shutdown 负责导出先于存储关闭，不重复关闭 DuckDB 域。
- workflow 的结果 result.status 与已存 attributes.status 需区分；固定版本运行中验证 outcome 可为空，endedAt 已存在。成功不等于业务资料齐全。
- 日志默认观测门槛 warn，本章显式 info，实际断言 listLogs 有关联片段的记录。console.log 不自动替代结构化 logger。
- hideInput/hideOutput 不覆盖独立日志；默认 SensitiveDataFilter 按字段，不保证自由文本隐私识别。自定义 sensitiveFields 替换默认列表。
- 指标口径限定当前实验时间；count 是匹配记录数。三个样本无需分页，正文明确生产需处理分页、分组和样本量。采样后的观测统计不未经校正视为全部流量。
- 本地工具 Span 不自动展示远端内部；跨系统上下文传播需双方对齐。requestId 元数据不承担鉴权。
- 三张图：记录管道、执行树、指标回查。执行树按实际 SDK 层级绘制，省略细节但不捏造工具直接挂 Agent 根节点。

## 验证

自定义 Node 24 检查运行正常/资料缺失/异常、输入输出隐藏与字段脱敏、日志 trace/span 关联、自动指标 count=3。Agent 保留真实 Mastra 执行循环，仅用固定 V2 模型替换远端响应，生成两次模型响应与工具片段；阻断远端 fetch，不产生付费请求。此验证不能证明网关账号权限、模型在线响应质量或生产性能。

JS/TS 内容、下载、目录路由及前后节链接需同步检查。SSR 与 SVG 检查不等于浏览器交互测试。不执行 pnpm build/lint/test，也不启动 dev。

最终复核：16 章共 136 节，18 份正文 JS/TS 源码引用与文件一致；两种语言的七个无模型入口全部运行通过，智能体入口分别通过固定响应验证。419 个源码解析、9 种高亮语法加载、272 个语言版本页面与 63 个图示 SSR 通过，三张新 SVG 已查看；每个下载包 16 个文件与源码逐字匹配。同步时修正 Node.js 在 TS 文案中被误替换为 Node.ts 的问题。

## 本轮 polish

- 配置节先讲数据流和运行方式，再展示共享配置与查询入口；保留本章内存实验的必要说明，减少生产部署的旁枝。
- 请求关联新增标识对照表，业务单号与 requestId/runId/traceId/spanId 分别说明；不把重试固定描述成唯一对应关系。
- 执行结果明确“最后一步正常完成”和“需要继续但耗尽 maxSteps”的区别。
- 日志配置用 logging.level 解释，避免把整段对象塞进正文并加粗；采样说明与自动指标派生关系衔接。
- 指标补充 P95 的简明定义，避免首次出现“分位数”而不解释。诊断准确称为工作流步骤，不把模拟等待称为外部服务调用。
- 八道检查题收束为具体排查与后续使用决策；精简重复的限定与否定。
- 01、05、07、08 的终端输出改为必要字段表格，减少空字段与内部结构；未改变采集、存储和查询逻辑。同步 TS、正文引用和下载包。
